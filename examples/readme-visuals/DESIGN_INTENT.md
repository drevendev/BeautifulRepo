# PocketDiff: a design-intent brief

**Scope:** the fictional [PocketDiff README example](README.md), not a shipped CLI.
This brief explains decisions in the existing example. It is not a reusable brand
identity, a claim that the illustrated report was generated by software, or
instructions to copy the same layout into every repository.

## Reader and job

The imagined reader is a developer comparing two recurring CSV exports locally.
They need to know what would change, whether the files leave their computer,
and what the resulting report contains **before** deciding whether to investigate
a command-line tool. They should not need a product video to understand it.

**One-sentence promise:** compare two CSV exports locally and receive a
row-level change report without uploading either file.

## First-screen order

1. State the job and local-data constraint.
2. Show one representative report, **18 changed / 2 added / 1 removed**,
   with its output name `changes.csv`.
3. Place the illustrative input command next to those results.
4. Explain exactly which details are illustrative and where a real project
   would link installation, prerequisites and validation evidence.

This hierarchy earns its space: the reader can understand what the tool *would*
do even if no SVG loads. It is different from a page led by an adjective,
a stack of badges, or a hero illustration unrelated to the result.

## Existing evidence and accessibility choices

The [before/after page](README.md) deliberately provides **two local SVGs**:
[light](hero-light.svg) and [dark](hero-dark.svg). The `picture` element
selects the theme variant, with a normal `img` fallback. The alt text
and adjacent text repeat the actual illustrated labels and numbers. The SVGs
also contain title/description metadata. Essential status is expressed in
words and counts rather than color alone.

These design decisions make the *example* more understandable; they do not
establish complete browser, screen-reader, contrast, or zoom compliance.
There is no real PocketDiff package, executable `pocketdiff` command,
published benchmark, user testimonial, or actual CSV output to verify.
Any adaptation must replace the illustration and terminal transcript with
evidence from its own working product.

## Explicitly rejected choices

- **Badge wall:** no published build/download data exists for PocketDiff.
  Invented badges would take attention away from the report.
- **Generic gradient hero or copied mascot:** it adds no information about
  the input, output, or privacy boundary and risks an interchangeable identity.
- **Animation-only demo:** the report must still make sense when images,
  motion, or external assets are unavailable.

## Adaptation test

A maintainer borrowing this *method*, not the picture, should be able to
answer: Who arrives? What task are they trying to finish? What real output
can be captured? Does the screenshot match a reproducible command?
Can the same information be read without the image?
If any answer is missing, revise the evidence before choosing visual polish.
