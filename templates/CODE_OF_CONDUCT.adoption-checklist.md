# Code of conduct adoption checklist

Use this before adding a live `CODE_OF_CONDUCT.md`. It is intentionally not a code of
conduct itself.

## Choose the policy

- [ ] The selected policy matches the project's expected community behavior.
- [ ] Maintainers have read the complete policy, not only its summary.
- [ ] Attribution, license, version, and modification requirements are understood.
- [ ] Local additions are clearly distinguished from upstream text when required.

## Define scope

- [ ] The policy says where it applies: repository activity, chat, events, or other spaces.
- [ ] It says who is covered, including maintainers and project representatives.
- [ ] Examples of unacceptable behavior fit the project's actual community spaces.

## Make enforcement real

- [ ] A named maintainer group or role owns enforcement decisions.
- [ ] Consequences or escalation steps are documented.
- [ ] The process explains how reports are reviewed and how conflicts are handled.
- [ ] The maintainers are willing and able to apply the process consistently.

## Verify confidential reporting

- [ ] A private reporting route exists now.
- [ ] The route was tested from a reporter's point of view.
- [ ] The intended responder can access incoming reports.
- [ ] A reporter can bypass a recipient who is involved in the complaint.
- [ ] The project explains who can access reports and how sensitive information is handled.

If these checks are not satisfied, do not invent a contact address or pretend GitHub issues are
confidential. Keep the policy in draft form until a real route exists.

## Publish and connect it

- [ ] The final code of conduct lives in a GitHub-supported location.
- [ ] Contributor documentation links to it.
- [ ] Enforcement contacts and instructions are no longer placeholders.
- [ ] Required attribution is preserved.
- [ ] Maintainers re-read the rendered file after publication.
