# Security policy scaffold

> **Drafting template — not a live reporting policy.**
>
> Do not publish this file as `SECURITY.md` until every uppercase placeholder has been
> replaced with a verified project-specific statement or working contact route.

## Supported versions

STATE_WHICH_RELEASES_OR_BRANCHES_RECEIVE_SECURITY_FIXES

If the project does not yet make support commitments, say so directly rather than inventing a window.

## Private reporting route

REPLACE_WITH_A_VERIFIED_PRIVATE_REPORTING_ROUTE

Before publishing, test the route from the reporter's side and confirm that the intended
maintainer can receive a message. Do not substitute a public issue URL for a private route.
If you name GitHub Private Vulnerability Reporting, first verify that the repository setting
is enabled; a `SECURITY.md` file or the ability to create advisories does not enable it.

## Useful first-report details

When appropriate for the verified private route, ask for the affected revision, reproduction
conditions, observed impact, whether the problem is already public, and any known mitigation.
Do not require unnecessary personal information.

## What reporters can expect

STATE_ONLY_BEHAVIOR_THE_PROJECT_CAN_RELIABLY_PROVIDE

Do not promise response-time SLAs, confidentiality, staffing or reward programs unless they
actually exist and are authorized.

## Disclosure and credit

STATE_THE_PROJECT_SPECIFIC_DISCLOSURE_AND_CREDIT_PRACTICE

Keep sensitive details private while they are being handled. Publish only what the project
is authorized and ready to disclose.
