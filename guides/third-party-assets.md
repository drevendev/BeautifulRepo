# Trace third-party assets before publishing a README

A public README may show screenshots, diagrams, icons, fonts, badges, video,
sample data and code excerpts. A repository-wide `LICENSE` does not prove
that the maintainer owns or can relicense every item. An attractive screenshot
with unclear reuse rights is not a contribution-ready asset.

Use this workflow when adding **an asset you did not create entirely from
material you have permission to use**, or when reviewing existing media.
It is a practical evidence checklist, not legal advice or a license-compatibility
opinion. If the rights or obligations are unclear, omit the item until resolved.

## First: inventory what the reader will actually receive

For each file, embed, excerpt or derived image, record:

1. **Exact item and distribution path.** Is it committed in `assets/`, hotlinked
   into the README, embedded in a release, or generated by a build? Check
   exported copies, thumbnails and social previews too.
2. **Origin and creator.** Record the original source page, author/rightsholder
   if known, acquisition date and the exact revision or download. A search
   result, screenshot of a website, or image with a watermark is not a license.
3. **Permission and conditions.** Keep a link to the *actual* license and its
   version, or to documented permission for this use. Check redistribution,
   modification, commercial and share-alike conditions where relevant. An
   open-source license on a code repository is not automatically permission
   for separate logos, trademarks, fonts, photographs or dataset contents.
4. **Transformations.** Note crops, recolouring, translations, composites or
   generated derivatives. Preserve required copyright and license notices,
   acknowledge changes when required, and do not imply the creator endorsed
   this project.
5. **Reader access.** Put the necessary credit/notice in an accessible, stable
   place visible to downstream users. An image's `alt` text describes its
   *information*; it is not a substitute for a license notice. Provide a text
   equivalent for material needed to understand the project.
6. **Disposition.** Choose `approved` with recorded evidence, `pending`
   (do not publish) or `removed/replaced`. Recheck if the asset changes.

Copy the [asset record template](../templates/ASSET_PROVENANCE.template.md)
into a project-owned third-party notice or review record, then remove all
placeholder content. Keep confidential permission correspondence outside a
public repository; publish only a permitted summary of the rights granted.

## An illustrative review: three different decisions

Imagine a fictional CLI repository preparing its first README:

- **Locally generated graph from synthetic CSV.** The contributor owns the
  plotting code, created the fake data and checked the graph for borrowed
  artwork or third-party datasets. Record generator/source revision, input
  provenance and what the graph demonstrates. It may be included *after*
  verifying actual ownership and distribution rights. Include a caption and
  text summary; the chart alone is not an accessible first success.
- **Icon from a source explicitly offered under CC BY 4.0.** Before including
  it, verify that the *particular icon* has that license, not merely the
  gallery's general footer. Keep the creator, source URL, license link,
  changes and credit. The CC BY 4.0 deed requires appropriate attribution,
  a license link and an indication of changes without suggesting endorsement.
  If an additional asset-specific restriction conflicts, do not treat the
  badge "CC BY" as overriding it.
- **Attractive photo found through image search, with no verifiable grant.**
  Do not commit or hotlink it. Replace it with an original illustration or
  material with verified permission. Writing "credit to the author" does not
  itself give permission to redistribute or adapt a photo.

These are **hypothetical assets**, not downloadable resources or a claim that
a specific photograph/icon is licensed. The same checks apply to AI-assisted
art: record the tool, input provenance and applicable provider terms instead
of declaring the output copyright-free or assuming rights over third-party
inputs, names, likenesses or logos.

## One concrete notice from this repository

BeautifulRepo's [third-party notices](../THIRD_PARTY_NOTICES.md) identify a
small workflow pattern adapted from a **specific pinned MIT-licensed source**
and reproduce its required copyright and permission notice. That example
covers that borrowed code pattern; it is **not** a license or provenance
certificate for every image, font, third-party website or generated fixture
in this repository.

A repository can keep its own MIT `LICENSE` unchanged while respecting
separate obligations on particular borrowed material. Do not silently modify
upstream license text or swap a source's notice for the project's own MIT
heading. For more complex combinations, ask someone qualified to assess
compatibility before distributing.

## Review this in a pull request

A contributor should make the proposed media visible for review, name its
source and terms, add the notice in the same change, describe alterations,
and test that all local README/media links work. A maintainer then checks the
actual source page and evidence rather than accepting a filename,
"free-to-use" search filter, license badge or generated provenance claim.

A useful rejection is precise: "This added `assets/banner.png` but gives
no verifiable right to redistribute it. Please supply the exact source and
permission terms, or use an original replacement." Do not assert infringement
from missing evidence alone; mark the permission **unverified**.

## Sources and boundaries

Source review: **2026-11-10**. Official background:

- [Open Source Guides — The Legal Side of Open Source](https://opensource.guide/legal/)
  distinguishes code licenses from separately licensed non-code materials.
- [GitHub Docs — Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
  explains that public visibility is not permission for third-party reuse.
- [Creative Commons — Attribution best practices](https://wiki.creativecommons.org/wiki/Best_practices_for_attribution)
  describes title, author, source and license (TASL) and changed-work credit.
- [Creative Commons — CC BY 4.0 deed](https://creativecommons.org/licenses/by/4.0/)
  describes the conditions for that **specific** license, not for other works.

This page does not inspect any live asset automatically, grant rights, verify
a creator's ownership or determine whether exceptions such as fair use apply.
Different licenses, jurisdictions, trademarks, privacy and personality rights
may require different treatment.
